# 应用说明：缺陷外推、审核排程与渠道签发

本文档说明 `releaseqa` 应用的业务规则、状态文件与命令用法。资料字段口径见
[资料契约.md](资料契约.md)。所有数据均为合成虚构数据。

## 1. 业务对象与证据模型

### 1.1 两层身份

* **条目（item）**：文本、语音、字幕素材，带内容指纹 `fingerprint` 与译作者。
* **引用（reference）**：条目在具体场景/分支中的使用，带独立的上下文指纹 `context`、
  受众暴露权重 `audience_weight` 与风险层 `risk`。

同一条目可被多个引用共用（资料中每个条目恰好被两个引用使用）。因此：

| 缺陷作用域 | 传播规则 |
| --- | --- |
| `content` 内容缺陷 | 挂在条目内容指纹上，同指纹的全部引用共同承担 |
| `context` 上下文缺陷（截断、时序、上下文错误） | 只属于对应引用，不传播 |

### 1.2 证据适用性（跨版本继承规则）

一条审核记录能否用于目标版本，由 `model.review_applicability` 判定：

1. 审核版本晚于目标版本 → 当时证据尚不存在，不可用；
2. `content` 证据：审核早于条目换版 → 针对旧指纹，失效（`item-changed`）；
3. `context` 证据：审核早于条目换版 → 失效；审核早于其上下文被
   `invalid_contexts` 宣告失效的版本 → 失效（`context-invalidated`）；
4. 其余情况适用。

关键点：失效是**时点关系**。换版之后新做的审核针对新素材/新时序，是适用证据，
不会因为上下文出现在历史失效名单里而被连坐。条目编号保持不变但指纹变化时，
旧证据一律不得继承。

### 1.3 三类审核记录的身份

| purpose | 含义 | 能否外推整层发生率 |
| --- | --- | --- |
| `random` | 风险层内等概率抽检，带 `inclusion_probability` | 可以，是唯一的概率样本来源 |
| `complaint` | 主动投诉触发的定向审核 | 不可以，投诉量不是发生率 |
| `recheck` | 定向复查 | 不可以，但可关闭/刷新缺陷状态 |

复查合格（`recheck` + `severity=none`）会关闭对应缺陷，但**原 random 记录仍保留
抽样身份**，估计的样本基数不缩小。普通抽检或投诉看到 `none` 不关闭已开启缺陷，
只有定向复查可以。

## 2. 缺陷台账（defects.py）

`build_ledger(data, version, extra_reviews)` 归约出目标版本的缺陷状态：

* **开启缺陷（findings, open=True）**：最新适用结论为非 none 且未被复查关闭；
* **失效发现（voided_findings）**：旧的非 none 发现因换版/时序替换失效，既不能
  证明缺陷仍在，也不能证明已消除；
* `resolved_by_review` / `resolved_severity` 记录失效后是否出现新的适用复查；
* 内容缺陷的 `propagated_to` 列出同一条目的其他受影响引用。

失效的 **critical** 发现不会被默认当作安全：渠道闸门要求必须有新的适用复查
且结论为 `none`，否则按「关键证据缺口」处理。

## 3. 风险层估计（estimation.py）

### 3.1 估计量

对每个风险层分别估计「重大（major 及以上）缺陷引用的受众暴露占比」：

* 分析单元为引用；样本仅含适用的 `random` 记录，权重为
  `audience_weight / inclusion_probability`（Horvitz-Thompson 加权）；
* 点估计为加权缺陷权重 / 加权总权重；
* 不确定性用固定种子（`20261123`）的加权自助法（1000 次）取百分位置信区间，
  结果可复现；另附无权重 Wilson 区间作交叉核对。

### 3.2 不可外推的情形

层内概率样本少于 2 条时，`extrapolable=false`，不返回点估计与区间，只给已知事实
（样本数、投诉/复查/失效引用清单）。`overall_exposure` 在任一层不可外推时拒绝
给出单一平均比率，`missing_strata` 显式列出缺证层——避免平均质量掩盖关键分支缺证。

输出中投诉引用（`complaint_refs`）、复查引用（`recheck_refs`）、失效引用
（`voided_refs`）分别列示，不与概率样本混算。

## 4. 审核排程（planning.py）

### 4.1 两类任务，目的严格区分

| 目的 | 触发条件 | 标记 |
| --- | --- | --- |
| `directed` 定向核验 | 失效证据（含失效的 none 结论）、开启的 critical 缺陷、内容缺陷传播命中、主动投诉 | `extrapolable=false`，无纳入概率 |
| `random` 随机补样 | 风险层概率样本不足、引用尚无适用抽检 | `extrapolable=true`，保留设计纳入概率（资料现行为 0.4） |

### 4.2 约束

* 审核员必须同时具备语种与全部所需内容类型资质，且不能复核自己参与翻译的条目；
* 剧情组（groups）必须成组查看：计划按语种取组内成员组成一个组任务，按整组
  `audit_hours` 计工时（即使只审组内部分语种成员，也需通读整组上下文）；
* 已接受（accepted/completed）任务占用工时；退回（returned）与换版失效
  （invalidated）释放未完成任务的工时，已完成任务不退工时；
* 已接受任务不会被新投诉或换版静默取消：`invalidate` 显式登记失效原因与
  `redispatch_scope`，完整事件轨迹保留。

资料表 `task_history` 中的历史工单通过 `_all_tasks` 合并进工时与排程视图；
首次对其登记失效时，会先补写 propose/accept 事件再写 invalidate。

## 5. 渠道闸门与签发（release.py）

### 5.1 五项闸门检查（针对渠道 × 语种 × 版本的内容集合）

1. `required_strata_coverage`：渠道要求的每个风险层都有可外推证据；
2. `major_exposure_limit`：各层重大缺陷暴露的置信上界不超过渠道阈值
   （pc 0.05、console 0.03，置信水平 0.95）；
3. `block_severity_closed`：禁止带出的严重度（critical）无开启缺陷（含传播命中）；
4. `voided_blocker_evidence_replaced`：失效的阻断级证据已有结论为 none 的新复查；
5. `story_group_integrity`：`must_deliver_together=true` 的剧情组在集合内
   同进退，不能只交付组内部分成员。

**全部通过才可发布**。负责人的三种选择：

* `continue_sampling` 继续抽检（闸门已全过时不允许以此名义暂缓）；
* `release_qualified_subset` 只发布满足条件的子集，须用 `--references` 显式
  指定交付引用，子集同样必须通过全部五项检查；
* `hold_channel_version` 暂缓整个渠道版本（任何时候都可登记）。

### 5.2 共享素材的连锁效应

一个共享语音/字幕修复可能同时解禁多个渠道（同一引用出现在 pc 与 console 集合中）；
但替换音轨会使 `invalid_contexts` 所列上下文的字幕时序证据失效，相关渠道的证据
覆盖条件可能同时由满足变为不满足，必须重新取证后才能恢复签发。

### 5.3 回执、撤回与不可篡改历史

* `receipt-register` 登记渠道接收回执，**回执才是实际上架事实**；`receipts`
  合并资料表初始回执与状态层新回执，同一集合以最新回执为准；
* `withdraw --item <条目> --severity <严重度>` 列出所有仍在线、且使用该条目
  的内容集合，给出「下架整个集合」与「仅撤回受影响引用」两种范围，同时列出
  可保留的其他在线版本；
* 签发事件只追加、不可改写；撤回查询不修改历史签发，统计更正以新事件体现。

## 6. 本地状态与资料包（store.py）

状态目录（默认 `state/`，已被 Git 忽略）包含四个追加式 JSONL：

| 文件 | 内容 |
| --- | --- |
| `review_events.jsonl` | 后续到达的审核记录（表结构与 data/reviews 一致） |
| `task_events.jsonl` | 任务事件：propose / accept / complete / return / invalidate |
| `signoff_events.jsonl` | 不可变签发决策及其闸门快照 |
| `receipt_events.jsonl` | 后续渠道接收回执 |

`export` 产出 `releaseqa-bundle-v1` 资料包，可在后续版本工作区用 `import-bundle`
导入。导入按主键/事件内容去重，不覆盖既有事件。后续版本会重新计算证据适用性，
而不是按条目编号直接继承旧结论。

## 7. 命令清单

全局参数 `--root`、`--state` 置于子命令之前。

```sh
# 分析与排程
analyze --language de --version 2 --channel pc
plan    --language de --version 2 --channel pc [--commit --on YYYY-MM-DD]

# 审核记录（含资质与自译校验）
add-review --id N1 --reference X099 --version 2 --reviewer U06 \
           --purpose recheck --scope context --severity none --on 2026-10-03
# random 记录需带 --inclusion-probability；complaint/recheck 不带

# 任务生命周期
task-accept   --task P2-de-001 [--reviewer U03] --on 2026-10-02
task-complete --task P2-de-001 --on 2026-10-04
task-return   --task P2-de-001 --reason 排期冲突 --on 2026-10-03
invalidate    --version 2 --on 2026-10-05

# 闸门、选项与签发
gate     --content-set V2-de-pc
options  --content-set V2-de-pc
signoff  --id S1 --content-set V2-de-pc \
         --decision release_qualified_subset \
         --references X019,X126,X127 --on 2026-10-06
# decision 另可选 continue_sampling / hold_channel_version

# 回执与撤回
receipt-register --id D1 --content-set V2-de-pc --channel-state online --on 2026-10-20
receipts
withdraw --item I001 --severity critical

# 跨版本资料包
export --out outputs/bundle.json
import-bundle --bundle outputs/bundle.json
```

## 8. 端到端测试观察点

`tests/test_shared_change.py` 以资料中的 CH1（条目 I001 在 v2 换音轨，失效
ctx-1/ctx-17）为主线，断言同一次共享素材变化同时引起：

1. **抽样证据**：X001/X181 的 v1 抽检在 v2 失效，两个风险层留下失效标记，
   但其他概率样本仍支撑层级可外推；
2. **审核任务**：已接受的 v1 工单 T-old 被显式 invalidate，事件轨迹完整，
   重派范围精确到 X001/X181，工时释放；
3. **渠道范围**：pc 与 console 两个德语集合同时出现阻断级证据缺口，一次
   定向复查合格后两个集合的该条件同时解除；
4. **历史不可变**：签发登记后再次分析不改动既有签发事件；资料包可导出并
   在新工作区完整导入。
